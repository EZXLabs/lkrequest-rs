# Benchmark 方法与发布门槛

lkrequest 的 benchmark 用于回答具体工程问题，不用于脱离环境宣称“最快”。所有公开结果必须让读者能够复现 workload、识别测量边界，并区分请求性能与指纹一致性。

## 测量分类

| 类型 | 主要问题 | 必须记录 |
|---|---|---|
| 请求级基准 | 连接复用、并发、吞吐和延迟 | workload、并发、连接数、p50/p95/p99、失败数 |
| 协议路径基准 | TLS、H2、H3、代理等路径成本 | 协议、握手策略、DNS、代理、回退行为 |
| 进程级基准 | CLI 冷启动或完整进程耗时 | 构建方式、启动次数、进程边界 |
| 指纹验证 | 实际线缆字段是否匹配目标浏览器 | 浏览器版本、抓包目标、字段规范化、差异 |

请求性能不能替代指纹验证。Hyperfine 等进程级工具适合测量命令启动到退出的端到端时间，不适合代替可复用 client 内部的请求延迟分位数。

## 公平 workload

比较多个客户端时，应保持下列条件一致：

- 使用相同协议、响应体、请求数、并发和连接复用策略；
- 完整消费并校验响应体，不能只测收到 headers；
- 在正式计时前预热连接和运行时；
- 交替客户端运行顺序，避免固定顺序吸收系统漂移；
- 至少报告多轮聚合结果，而不是挑选最快一轮；
- 同时记录吞吐、p50、p95、p99、失败数、连接数和资源使用；
- 将 TLS、DNS、代理、压缩、重定向等开关写入结果，不允许隐含。

## 标准报告字段

每份结果至少包含：

1. 源码 revision、依赖版本和构建 profile；
2. 操作系统、kernel、CPU/虚拟化环境和 Rust toolchain；
3. server 与 client 的 socket、runtime 和 CPU affinity 配置；
4. 每个场景的 body 大小、请求数、并发、Session 和连接数；
5. 预热次数、正式轮次、运行顺序和聚合方法；
6. 原始机器可读结果的位置与完整性校验；
7. 已知污染、失败和不适合外推的边界。

## 发布门槛

`docs/data/benchmark-index.toml` 是公开结果索引。只有同时满足以下条件的数据集才能标记为 `publishable = true`：

- workload 与环境信息完整；
- 原始 JSON/JSONL 或等价机器可读数据进入公开归档；
- 多轮结果和延迟分位数可由原始数据重新计算；
- 所有正式轮次的失败与异常均已说明；
- 报告没有把共享虚拟机或 loopback 结果外推为跨机器排名；
- benchmark revision 与结果文件能够对应。

不满足门槛的结果仍可作为工程证据展示，但必须明确标记为不可发布的内部/诊断基线，不能作为 README headline 或发布宣传数据。
