# Streaming Uploads

`RequestBuilder::body_reader` and `body_stream` upload incrementally over HTTP/1.1,
HTTP/2 and, with `quic-h3`, HTTP/3. They work with both `send()` (buffered download)
and `send_streaming()` (incremental download).

## API Selection

The synchronous and asynchronous builders have methods with the same name, but
they are different Rust types and accept different reader traits:

| Builder | Upload method | Source | Send call |
| --- | --- | --- | --- |
| `lkrequest::session::RequestBuilder` | `body_reader(reader, length)` | `tokio::io::AsyncRead + Send + 'static` | `.send().await` |
| `lkrequest::session::RequestBuilder` | `body_stream(stream, length)` | `Stream<Item = io::Result<Bytes>> + Send + 'static` | `.send().await` |
| `lkrequest::blocking::RequestBuilder` | `body_reader(reader, length)` | `std::io::Read + Send + 'static` | `.send()` |

All three take `Option<u64>` for `length`. Sources are owned by the request, so
pass an owned file rather than a borrowed local reader. Async readers and streams
need not implement `Unpin`. The builder calls themselves do not read or send data.
Setting another body replaces the previous source.

Upload mode and response mode are independent: `send_streaming()` does not turn
an existing `.body(bytes)` into a streaming upload. Conversely, `body_reader()`
with `send()` uploads incrementally but buffers the response. The blocking API
has no separate `body_stream()` method.

## Asynchronous Files

```rust,no_run
# async fn upload(session: &lkrequest::Session) -> Result<(), Box<dyn std::error::Error>> {
let file = tokio::fs::File::open("archive.zip").await?;
let length = file.metadata().await?.len();
let response = session.post("https://example.com/upload")
    .body_reader(file, Some(length))
    .send()
    .await?;
assert!(response.status().is_success());
# Ok(())
# }
```

Pass `None` instead of a length for sources whose size is unknown. HTTP/1.1 uses
chunked transfer encoding; HTTP/2 and HTTP/3 use DATA frames without a
`Content-Length` header. Do not set `Transfer-Encoding` yourself.

`body_stream(stream, length)` accepts any `Send + 'static` implementation of
`futures_core::Stream<Item = std::io::Result<bytes::Bytes>>`, including streams
that are not `Unpin`. Empty chunks are skipped and source errors abort sending.
Readers are polled in bounded chunks. Byte streams should themselves produce
reasonably sized chunks; the library does not shrink a chunk's backing allocation.

## Generated Byte Streams

For a producer that already emits chunks, use `body_stream()`. This example uses
the optional application dependency `futures-util = "0.3"` for its stream adapter:

```rust,ignore
use bytes::Bytes;
use futures_util::stream;

let chunks = stream::iter([
    Ok::<_, std::io::Error>(Bytes::from_static(b"first chunk\n")),
    Ok(Bytes::from_static(b"second chunk\n")),
]);
let mut response = session.post("https://example.com/upload")
    .header("content-type", "application/octet-stream")
    .body_stream(chunks, None)
    .send_streaming()
    .await?;

while let Some(chunk) = response.chunk().await? {
    // Consume response bytes without collecting the whole response.
    process(chunk);
}
```

For a channel-backed producer, use a bounded channel and drop every sender when
production finishes. Keeping a sender alive prevents EOF. Backpressure in the
transport does not bound an unbounded channel or a producer's own buffers.

## Synchronous Files

```rust,no_run
# fn upload(session: &lkrequest::blocking::Session) -> Result<(), Box<dyn std::error::Error>> {
let file = std::fs::File::open("archive.zip")?;
let length = file.metadata()?.len();
let response = session.post("https://example.com/upload")
    .body_reader(file, Some(length))
    .send()?;
assert!(response.status().is_success());
# Ok(())
# }
```

Blocking readers run on a blocking worker, one bounded read at a time. A read
already executing cannot be forcibly interrupted. Configure a read timeout on
synchronous network readers that might otherwise block indefinitely.

## Lengths, Retries and Middleware

- A supplied length is exact. Short or oversized sources fail; an explicit
  `Content-Length` must agree with it. An explicit length on an unknown-size
  source becomes its checked length. Length checking requires observing EOF,
  so close the producer after its last chunk.
  The final chunk is retained until EOF is checked, including for HTTP/1.1 where
  the transport could otherwise stop polling once `Content-Length` is satisfied.
  A declared zero length is also checked; it does not discard a nonempty source.
- Streams are single-use. Once a transport claims the source, automatic retry
  and protocol fallback cannot replay it, even for idempotent methods. Recreate
  the source to retry explicitly. Streaming uploads do not use HTTP/3 0-RTT.
- `send()` follows body-dropping redirects normally. Redirects requiring the
  consumed body fail. `send_streaming()` retains its existing behavior of
  returning the first response without automatic redirects or session retries.
- Request middleware sees `None` for a streaming body; it may still change the
  method, URL and headers. Setting a buffered body in middleware replaces the
  stream. Sources are never collected merely to run middleware.
  Once any middleware replaces the stream, later middleware removing that
  replacement does not restore the original stream.
- Existing `body`, JSON, form and Multipart uploads retain their buffered
  behavior. C ABI upload setters also remain buffered; the new upload-source
  interfaces are Rust APIs.

## Cancellation and Early Responses

Dropping an in-flight request future or reaching its request deadline stops the
upload. A synchronous read already running in the blocking pool is the exception
described above. Upload EOF does not end the request's lifetime: cancellation while
waiting for a response still releases the HTTP/2 stream.

A server can reject an upload before consuming it, for example with status 413.
HTTP/3 receives response headers concurrently with sending. HTTP/1.1 discards a
connection whose upload is still incomplete when the response is finished, rather
than returning it to the pool. Consume or drop a streaming response to release its
resources; receiving headers alone is not proof that the request body was accepted.

An upload error does not roll back bytes already sent or server-side effects.
Inspect the response status, and apply application-level idempotency rules before
opening a fresh source for an explicit retry. No upload byte limit is implied by
response resource limits; enforce any upload quota in the application.
